📚 PART 1: Understanding CPU & Memory

What is CPU? (Think of it as a Cashier)

A cashier at a store:
• One cashier can handle one customer at a time
• If 100 customers come, the cashier is overwhelmed
• The cashier works very fast (calculations per second)

On a server:

  • CPU does calculations and processes requests
  • When CPU is 100%, it's like the cashier handling 100 customers at once
  • When CPU is 50%, the cashier is half-busy
  • When CPU is 0%, there's nothing to do
CPU Usage Status What It Means
0-20% ✅ Server Relaxed Light work, plenty of capacity
20-50% ✅ Moderate Work Normal, website responds fast
50-80% ⚠️ Busy Working hard but OK
80-95% ❌ Very Busy Website slow, users complain
95-100% 🚨 CRITICAL Website frozen! Users can't access!

What is Memory (RAM)? (Think of it as a Desk)

A desk in an office:
• Bigger desk = you can have more papers on it
• When desk fills up, you can't work efficiently
• When desk is full, you waste time cleaning up

On a server:

  • Memory is where programs store data they're using RIGHT NOW
  • When you open an app, it uses RAM
  • When RAM fills up, server gets slow (uses disk instead)
  • When RAM is completely full, server crashes
Memory Usage Status What It Means
0-50% ✅ Server Relaxed Plenty of free space
50-70% ✅ Normal Good, server working normally
70-85% ⚠️ Getting Full Still OK but watch it
85-95% ❌ Very Full Server getting slow
95-100% 🚨 CRITICAL Server crashes! Services fail!

STEP 2: Check What's Running (TOP Command)

What is the TOP command?

TOP is like a LIVE DASHBOARD that shows:

  • How much total CPU is being used
  • How much total Memory is being used
  • Which programs are using the most resources
  • Real-time updates

The Command:

top -bn1 | head -20

Breaking it down:

  • top = Show system resources
  • -bn1 = Show it once and exit (don't wait for input)
  • | head -20 = Show only first 20 lines (don't show all output)

Output:

top - 14:30:45 up 45 days, 3:22, 2 users, load average: 8.45, 7.23, 6.12 Tasks: 156 total, 12 running, 144 sleeping, 0 stopped, 0 zombie %Cpu(s): 95.2 us, 3.1 sy, 0.0 ni, 1.5 id, 0.2 wa MiB Mem : 16000.0 total, 14720.0 used, 1280.0 free, 250.0 buff MiB Swap: 4096.0 total, 2048.0 used, 2048.0 free. 3200.0 avail Mem PID USER PR NI VIRT RES %CPU %MEM TIME+ COMMAND 5678 mysql 20 0 2456012 8456m 45.2 52.8 156:32 mysqld 1234 www-data 20 0 856204 3200m 38.1 20.1 89:45 php-fpm 9012 root 20 0 156204 245m 8.5 1.5 12:30 sshd

Understanding Line 1: Current Time

top - 14:30:45 up 45 days, 3:22, 2 users, load average: 8.45, 7.23, 6.12

What this means:
• Current time: 14:30:45 (2:30 PM)
• Server running: 45 days (good, no recent reboot)
• Users logged in: 2
• Load average: 8.45 = VERY BUSY!

What is "Load Average"?

Think of it like HOW BUSY IS THE CASHIER:

  • Load 1.0 = 1 cashier exactly busy (normal)
  • Load 2.0 = 2 cashiers worth of work (on 1 cashier = slow!)
  • Load 8.45 = 8.45 cashiers worth of work (CRITICAL!)

On a server:

  • If you have 4 CPU cores: Load 4.0 = Normal
  • If you have 4 CPU cores: Load 8.45 = TWICE as many tasks!
  • Load 8.45 is CRITICAL! ❌

Understanding Line 3: CPU Usage

%Cpu(s): 95.2 us, 3.1 sy, 0.0 ni, 1.5 id, 0.2 wa

What this means:
• 95.2% used by user programs = 95.2% BUSY ❌
• 3.1% used by system
• 1.5% idle = almost NO free capacity!

Translation: CPU is 95% busy. Critical!

Understanding Line 4: Memory Usage

MiB Mem : 16000.0 total, 14720.0 used, 1280.0 free

What this means:
• Total RAM: 16000 MB = 16 GB
• Used RAM: 14720 MB = 14.7 GB
• Free RAM: 1280 MB = 1.3 GB

Calculation: 14720 / 16000 = 92% used ❌
Only 1.3 GB free!

Understanding the Process List (MOST IMPORTANT!)

Look at this part:

PID %CPU %MEM COMMAND
5678 45.2 52.8 mysqld ← Using 45% CPU + 52% memory!
1234 38.1 20.1 php-fpm ← Using 38% CPU + 20% memory!
9012 8.5 1.5 sshd ← Using 8% CPU + 1% memory

The Problem Found:
1. MySQL is using 45.2% CPU + 52.8% memory = HUGE!
2. PHP is using 38.1% CPU + 20.1% memory = VERY HIGH!
3. Together = 83% CPU + 72% memory!

These two processes are killing the server!

What you're thinking: "MySQL is using way too much CPU and memory! And PHP is also high. Something is wrong. Let me check what queries MySQL is running."

STEP 3: Check What MySQL Is Doing

The Command:

mysql -u root -p -e "SHOW PROCESSLIST;" 2>/dev/null

What this does:

  • Connects to MySQL database
  • SHOW PROCESSLIST = Show all queries running RIGHT NOW
  • Shows WHY MySQL is using so much CPU

Output:

+----+------+-----------+--------+---------+------+-------+------------------+ | Id | User | Host | db | Command | Time | State | Info | +----+------+-----------+--------+---------+------+-------+------------------+ | 1 | root | localhost | mysql | Query | 892 | copy to tmp table | SELECT * FROM orders WHERE status='pending' | | 2 | user | localhost | myapp | Query | 456 | Sorting result | SELECT * FROM users JOIN orders ON... | | 4 | user | localhost | myapp | Query | 234 | copy to tmp table | SELECT COUNT(*) FROM large_table WHERE... | +----+------+-----------+--------+---------+------+-------+------------------+

Understanding Query 1:

Field Value Meaning
Id 1 Query ID (used to kill it)
Time 892 seconds 14+ MINUTES! ❌
State copy to tmp table Creating temporary table in RAM (CPU intensive!)
Query SELECT * FROM orders WHERE status='pending' Getting all pending orders (no LIMIT!)
Why 892 seconds is BAD:

• Normal query: 0.1 to 1 second
• This query: 892 seconds
• This is 900 TIMES SLOWER than normal!

This query is STUCK and consuming massive CPU!

Query 2 and 4 are also bad:

  • Query 2: Running 456 seconds (7+ minutes!)
  • Query 4: Running 234 seconds (3+ minutes!)
THE ROOT CAUSE DISCOVERED:

You found 3 queries running for 892, 456, and 234 seconds!

Why this is a problem:
• These queries should complete in < 1 second
• They're stuck and consuming massive CPU
• They're hogging RAM (creating temp tables)
• New requests are piling up behind them
• Website becomes slow/frozen

What you're thinking: "These queries are CRAZY! I need to stop them immediately. Once I kill them, the server should recover."

STEP 4: Kill the Worst Query

The Command:

mysql -u root -p -e "KILL 1;" 2>/dev/null

What this does:

  • KILL 1 = Stop query with ID 1
  • Immediately terminates the 892-second query
  • MySQL stops using CPU and RAM for this query
  • Result: Instant resource recovery

Output:

(no output = query successfully killed)

Immediately Check CPU/Memory:

Command:

top -bn1 | head -10

BEFORE Killing Query

%Cpu(s): 95.2 us ← 95% CPU
MiB Mem: 14720 used ← 92% memory

AFTER Killing Query

%Cpu(s): 45.2 us ← 45% CPU ✅
MiB Mem: 9234 used ← 57% memory ✅
AMAZING IMPROVEMENT!

• CPU dropped from 95% → 45% ✅
• Memory dropped from 92% → 57% ✅
• One query was using 50% of all resources!

What you're thinking: "Wow! Killing one query freed up 50% of resources! But there are still 2 more slow queries. Let me kill them too."

STEP 5: Kill the Other Slow Queries

The Command:

mysql -u root -p -e "KILL 2; KILL 4;" 2>/dev/null

This kills:

  • Query ID 2 (456 seconds)
  • Query ID 4 (234 seconds)

Check Again:

Command:

top -bn1 | head -10

BEFORE

CPU: 45%
Memory: 57%

AFTER

CPU: 8% ✅
Memory: 15% ✅
SERVER IS HEALTHY AGAIN!

• CPU dropped from 45% → 8% ✅
• Memory dropped from 57% → 15% ✅
• Crisis resolved!

What you're thinking: "Perfect! All slow queries are gone. The server is back to normal. But I need to find out WHY these queries were running. They must be from a background job or cron script."

STEP 6: Find What Triggered These Queries

The Command:

ps aux | grep -E "mysql|php" | head -10

What this does:

  • ps aux = List all running processes
  • grep -E "mysql|php" = Show only MySQL and PHP processes
  • Shows what's currently running and using resources

Output:

mysql 5678 0.5 2.1 2456012 340789 14:15 ? Sl 156:32 /usr/sbin/mysqld www-data 1234 1.2 1.5 856204 256789 14:15 ? S 89:45 /usr/sbin/php-fpm www-data 5690 0.0 0.1 45678 234 14:22 ? S 0:02 php /var/www/backup_orders.php
What this tells you:

• mysqld = Database (normal now, 0.5% CPU)
• php-fpm = Web server (normal now, 1.2% CPU)
• backup_orders.php = NEW! This is the culprit!

This script was executing those slow queries!

What you're thinking: "There's a script called `backup_orders.php` that was running the slow queries. This is the problem! Let me check when this script is scheduled to run."

STEP 7: Check Scheduled Jobs (CRON)

The Command:

cat /var/spool/cron/crontabs/www-data

What this does:

  • Shows all scheduled jobs for the www-data user
  • Cron jobs run automatically at specific times
  • No manual intervention needed

Output:

# Run backup every day at 2 PM 0 14 * * * /usr/bin/php /var/www/backup_orders.php # Run cleanup every 6 hours 0 */6 * * * /usr/bin/php /var/www/cleanup_old_data.php # Generate reports every Sunday 0 10 * * 0 /usr/bin/php /var/www/generate_reports.php

Understanding Cron Syntax:

Cron Time Meaning Description
0 14 * * * Every day at 2 PM 14:00 (2 PM)
0 */6 * * * Every 6 hours 0:00, 6:00, 12:00, 18:00
0 10 * * 0 Every Sunday at 10 AM Weekly
THE PROBLEM IDENTIFIED:

• backup_orders.php scheduled: 2 PM every day
• Current time: 14:22 (2:22 PM)
• Scheduled time: 14:00 (2:00 PM)
• Difference: 22 minutes ago

The backup job started 22 minutes ago and is still running!

What the script does:
• Executes: SELECT * FROM orders
• No LIMIT clause = pulls ALL orders
• Millions of rows!
• Server can't handle it → CPU/Memory maxed out
• Website frozen

What you're thinking: "Now I understand the problem completely! The backup script runs every day at 2 PM. It's trying to backup ALL orders without any optimization. This is why the server crashed. Tomorrow at 2 PM, it will run again and cause the same problem. I need to FIX this!"

🎓 What Went Wrong & How You Fixed It

The Problem:

  • CPU: 95% (too high)
  • Memory: 92% (too full)
  • Website: Slow and unresponsive

Root Cause:

  • backup_orders.php script ran at 2 PM
  • Script executed slow queries that:
    • Took 892, 456, 234 seconds to complete
    • Consumed massive CPU and RAM
    • Locked up the entire server

The Solution:

  • Identified slow queries using SHOW PROCESSLIST
  • Killed the queries using KILL command
  • CPU dropped from 95% to 8%
  • Memory dropped from 92% to 15%
  • Website became fast again

Prevent It Tomorrow:

  1. Optimize the script:
    • Add LIMIT clause to backup (last 7 days only)
    • Add WHERE clause to filter orders
    • Add query timeout (max 5 minutes)
  2. Reschedule:
    • Run backup at 2 AM instead of 2 PM
    • Avoid peak traffic hours
  3. Add monitoring:
    • Alert if query runs > 30 seconds
    • Alert if CPU > 80%
    • Alert if Memory > 80%
