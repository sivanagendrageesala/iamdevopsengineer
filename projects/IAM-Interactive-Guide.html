AWS IAM Explained

Identity and Access Management — Interactive Learning Guide

🔐 What is IAM?

IAM = Identity and Access Management — AWS's service for controlling who (identities) can do what (permissions) with your AWS resources. It's the security foundation of AWS.

Users

Individual people or applications with specific permissions

Groups

Collections of users with shared permissions

Roles

Sets of permissions assumed by users or services

Policies

JSON documents that define specific permissions

⚠️ Critical: The Root Account (AWS account owner) has complete access to everything. Don't use it for daily work. Create IAM users instead and follow the principle of least privilege.

👤 IAM Users

An IAM user is an identity with specific permissions for a person or application. Each user has their own credentials (passwords and access keys).

User Demo

IAM Users:

alice@company.com Admin
bob@company.com Developer

Access Keys

Every IAM user can have up to 2 access key pairs (for API access). Each key has:

  • Access Key ID: Unique identifier (like a username)
  • Secret Access Key: Password-like secret (never share!)

Authentication Methods

Console Login

✓ Username + Password

✓ MFA (optional but recommended)

For AWS Console access

Programmatic Access

✓ Access Key ID + Secret

✓ Used by CLI, SDK, applications

For automated API calls

👥 IAM Groups

A group is a collection of IAM users. Groups simplify permission management by applying policies to multiple users at once.

Group Structure

📁 Engineering Group
└─ alice (member)
└─ bob (member)
└─ charlie (member)
✓ Policies Attached:
└─ EC2FullAccess
└─ S3ReadOnly
💡 Best Practice: Create groups based on job function (Engineers, Developers, Finance) and attach policies to groups, not individual users.

🎭 IAM Roles

A role is a set of permissions that can be assumed by users or AWS services. Roles are useful for cross-account access and service-to-service communication.

Key Differences: Users vs Roles

IAM Users

✓ Have permanent credentials

✓ Used by people

✓ Console + API access

IAM Roles

✓ Have temporary credentials

✓ Used by services/applications

✓ Automatically rotated

Common Role Use Cases

EC2 Instance Role

Give EC2 instances permission to access S3, DynamoDB, etc.

Lambda Execution Role

Permissions for Lambda functions to use other AWS services

Cross-Account Access

Allow users from one AWS account to access another

Service Role

Allow AWS services to call other AWS services

📋 Policies & Permissions

An IAM policy is a JSON document that defines what actions are allowed or denied on what resources.

Policy Structure

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": Allow,
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}

Policy Components

Effect

Allow or Deny — whether this permission is granted or explicitly blocked

Action

What operation is permitted (e.g., "s3:GetObject", "ec2:DescribeInstances")

Resource

Which AWS resources the action applies to (e.g., specific S3 bucket)

Condition

(Optional) Additional conditions like IP address, time, MFA requirement

AWS Managed vs Customer Managed Policies

AWS Managed

Created and maintained by AWS (e.g., AdministratorAccess)

Updates applied automatically

Best for common use cases

Customer Managed

Created and maintained by you

Full control and customization

Better for specific requirements

🛡️ Principle of Least Privilege

The most important security principle in IAM: give users/services only the minimum permissions they need to do their job.

❌ Don't Do This

Attaching AdministratorAccess to developers:

  • Developers can accidentally delete production databases
  • No audit trail of who did what
  • Increases security risk

✅ Do This Instead

Create specific policies for developers:

  • EC2 full access (for dev/test instances only)
  • S3 access to specific dev buckets only
  • RDS read-only to production databases
  • No access to billing, IAM, or KMS

🔧 Troubleshooting Guide

Access Denied Errors

Step 1: Verify User Exists and is Attached to Policies

  • Go to IAM Users in AWS Console
  • Check if user has any policies attached
  • Verify user is in groups with permissions

Step 2: Check Policy Statements

  • Review the policy JSON for the correct Action
  • Verify Resource ARN matches what you're accessing
  • Check for any Deny statements that override Allow
  • Ensure Effect is "Allow" not "Deny"

Step 3: Check Conditions

  • If policy has conditions, verify they're met
  • Check IP address restrictions
  • Verify MFA requirements are satisfied
  • Check time-based conditions

Step 4: Use IAM Policy Simulator

  • Go to IAM > Access Analyzer > Policy Simulator
  • Simulate the action you're trying to perform
  • Check the detailed result explaining why it failed

Lost/Forgotten Root Account Password

Recovery Steps:

  • Go to AWS login page and click "Forgot Password"
  • Verify email associated with account
  • Reset password via email link
  • Enable MFA immediately after recovery

Cannot Assume Role

Checklist:

  • ✓ User has sts:AssumeRole permission
  • ✓ Role's trust policy allows the user's account/principal
  • ✓ No explicit Deny on role assumption
  • ✓ Role hasn't exceeded session duration

Locked Out of AWS Account

If All Admin Users Are Locked Out:

  • Root account: Use account recovery process
  • Billing contact: AWS Support can help with emergency access
  • Organization: Another org account's root user can help

✨ Security Best Practices

Never Use Root Account

Create IAM users for daily work, use root only for account setup

Enable MFA

Add multi-factor authentication to all user accounts

Least Privilege Access

Give only the minimum permissions needed

Regular Audits

Review user permissions and remove unused access

Rotate Keys Regularly

Change access keys every 90 days

Use Roles for Services

Attach IAM roles to EC2/Lambda instead of embedding keys
