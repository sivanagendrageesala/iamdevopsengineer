📚 PART 1: Understanding Backups (The Basics)

What is a Backup? (Think of it as Insurance)

Real-world analogy:
• You have a house (= your database)
• You have homeowner's insurance (= backup)
• If house burns down, insurance pays to rebuild
• Without insurance, you lose everything

In DevOps:

  • Database = valuable data (customers, orders, transactions)
  • Backup = copy of that data stored safely
  • If database crashes, restore from backup
  • No backup = data gone forever = company loses everything

Why Backups Matter

Scenario With Backup Without Backup
Disk failure ✅ Restore from backup (1 hour) ❌ Data lost forever
Ransomware attack ✅ Restore clean version (few hours) ❌ Pay ransom or lose data
Accidental delete ✅ Restore deleted data (minutes) ❌ Data lost forever
Compliance audit ✅ Have backup proof (pass audit) ❌ Fail audit, get fined

🔍 PART 2: Understanding Why Backup Failed

Common Backup Failure Causes

Cause What Happened Error Message How to Fix
Wrong Credentials Backup user doesn't exist or password wrong Access denied for user 'backup' Create/update backup user
No Disk Space Server disk too full to save backup No space left on device Free up disk space
Network Down Can't upload to cloud storage Connection timeout Check network connection
Database Locked Database being used, can't backup Table is locked Wait or restart database
Script Error Backup script has bug or syntax error Command not found Fix script

🚀 PART 3: Step-by-Step Fix (Real Example)

STEP 1: Check Backup Log

The Command:

tail -100 /var/log/backup/backup.log

Output:

[2026-09-01 02:00:01] Starting backup job [2026-09-01 02:00:05] Connecting to database... [2026-09-01 02:00:06] ERROR: Access denied for user 'backup'@'localhost' [2026-09-01 02:00:06] Backup FAILED [2026-09-01 02:00:06] Deleting partial backup [2026-09-02 02:00:01] Starting backup job [2026-09-02 02:00:05] Connecting to database... [2026-09-02 02:00:06] ERROR: Access denied for user 'backup'@'localhost' [2026-09-02 02:00:06] Backup FAILED
⚠️ CRITICAL FINDING:

• Backup runs every day at 2 AM
• Every day: "Access denied for user 'backup'"
• This happened 7 times (7 days)
Root Cause: Backup user credentials are wrong!

What you're thinking: "The backup user can't authenticate. Either the user doesn't exist, or the password is wrong. Let me check the database."

STEP 2: Check If Backup User Exists in Database

The Command:

mysql -u root -p -e "SELECT user, host FROM mysql.user WHERE user='backup';"

Output:

(empty result - user doesn't exist!)
CONFIRMED:

• Backup user 'backup' does NOT exist
• That's why authentication fails
• Every night at 2 AM, the backup script tries to use non-existent user
• Connection is immediately rejected
Solution: Create the backup user with correct permissions

What you're thinking: "The backup user was deleted or never created. I need to create it with the right permissions so the backup script can authenticate."

STEP 3: Create Backup User with Permissions

The Command:

mysql -u root -p << 'EOF' CREATE USER 'backup'@'localhost' IDENTIFIED BY 'secure_backup_password_2026'; GRANT SELECT, LOCK TABLES, SHOW VIEW ON *.* TO 'backup'@'localhost'; GRANT RELOAD ON *.* TO 'backup'@'localhost'; FLUSH PRIVILEGES; EOF

Output:

Query OK, 0 rows affected Query OK, 0 rows affected Query OK, 0 rows affected Query OK, 0 rows affected

Understanding the Permissions:

Permission What It Does Why Needed for Backup
SELECT Read all data Backup needs to read all tables
LOCK TABLES Lock tables during backup Freeze data so backup is consistent
SHOW VIEW See view definitions Backup database views
RELOAD Flush logs Reset binary logs after backup
✅ Backup user created
✅ With correct permissions
✅ With secure password

What you're thinking: "Good! The backup user is created. Now I need to update the backup script to use the correct password."

STEP 4: Update Backup Script Credentials

Edit backup config:

sudo nano /etc/backup/backup.conf

Find and update these lines:

# BEFORE (Wrong credentials) MYSQL_USER=backup_user MYSQL_PASSWORD=old_password # AFTER (Correct credentials) MYSQL_USER=backup MYSQL_PASSWORD=secure_backup_password_2026 MYSQL_HOST=localhost MYSQL_PORT=3306

What you're thinking: "The backup script now has the correct credentials. Let me test it manually to make sure it works."

STEP 5: Test Backup Manually

The Command:

sudo /usr/local/bin/backup.sh

Output:

What you're thinking: "Perfect! The manual backup works. But I need to test that a restore actually works. Having a backup is useless if you can't restore it."

STEP 6: Test Restore (CRITICAL!)

Why this matters:

⚠️ Important: A backup that can't be restored is USELESS!
Many companies discover their backups don't work... when they try to restore after a disaster!
ALWAYS test restores regularly!

Create test database:

mysql -u root -p -e "CREATE DATABASE test_restore;"

Download backup from S3:

aws s3 cp s3://backups/myapp_backup_2026-09-01.sql.gz /tmp/backup.sql.gz

Decompress and restore:

gunzip /tmp/backup.sql.gz mysql -u root -p test_restore < /tmp/backup.sql

Verify data was restored:

mysql -u root -p -e "USE test_restore; SELECT COUNT(*) as 'Total Users' FROM users; SELECT COUNT(*) as 'Total Orders' FROM orders;"

Output:

+--------------+ | Total Users | +--------------+ | 5678 | +--------------+ +---------------+ | Total Orders | +---------------+ | 23456 | +---------------+
✅ Test database created
✅ Backup downloaded from cloud
✅ Data restored successfully
✅ Row counts match original database
RESTORE WORKS!

What you're thinking: "Excellent! The backup works AND the restore works. This proves the backup is actually usable. Now let me verify the cron job will run the backup every day."

STEP 7: Verify Cron Job Scheduled

The Command:

crontab -l | grep backup

Output:

# Backup runs at 2 AM every day 0 2 * * * /usr/local/bin/backup.sh >> /var/log/backup/backup.log 2>&1

Understanding Cron Syntax:

Field Value Meaning
Minute 0 At minute 0
Hour 2 At hour 2 (2 AM)
Day of Month * Every day
Month * Every month
Day of Week * Every day of week
✅ Cron job is configured
✅ Backup scheduled for 2 AM daily
✅ Logs are saved
✅ Will run automatically every day
STEP 8: Check Next Backup Runs Successfully

✅ Complete Fix Checklist

When backup fails, follow this checklist:

  1. ☐ Check backup log for error message
  2. ☐ Identify root cause (credentials, space, permissions)
  3. ☐ Create/update backup user in database
  4. ☐ Update backup script with correct credentials
  5. ☐ Run backup manually to test
  6. ☐ Test restore to verify backup is usable
  7. ☐ Verify cron job is scheduled
  8. ☐ Wait for next scheduled backup & confirm success
  9. ☐ Set up monitoring/alerts for backup failures

Total time: ~15 minutes
